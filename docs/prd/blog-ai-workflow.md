## 3. 문제

### 3.1 데스크리서치

#### 3.1.1 SWOT 분석

| 구분 | 내용 |
|---|---|
| 강점 (S) | 직접 만든 블로그라 기능을 자유롭게 붙일 수 있음. Firebase 로그인, GA4 이벤트, 글별 링크 미리보기가 이미 구현되어 있음. |
| 약점 (W) | 공개 글 4개가 모두 예시 글이고 시험 글("제목")이 공개 상태. 저자 소개가 없음. 첫 화면에 글이 없고 목록이 길며 본문 마크다운이 깨짐. sitemap, RSS가 없음. |
| 기회 (O) | 채용 담당자는 결과보다 판단 과정을 보고 싶어 함(개인 칼럼 근거). 같은 Firebase 프로젝트에서 Firebase AI Logic으로 API 키를 직접 다루지 않고 무료 Gemini를 쓸 수 있음. 이번 검색 기준으로 국내 주요 플랫폼에서 발행 전 점검형 AI는 확인되지 않음. |
| 위협 (T) | 검색에 AI 요약이 뜨면 클릭률이 낮아짐(Ahrefs: 1위 글 평균 58% 감소). AI가 쓴 글에 대한 불신이 커지는 중(Substack AI 탐지 기능). 큰 플랫폼과의 노출 경쟁. |

#### 3.1.2 3C 분석

| 구분 | 내용 |
|---|---|
| 자사 (Company) | 실제로 발행한 글 0편(공개 글 4개는 모두 2026-11-17 작성 예시). 작업 기록은 35건으로 기능 개발에 쏠림. 헤더에 명언, 공휴일, 시계 위젯. 방문자에게 글쓰기 링크가 보임. |
| 경쟁 (Competitor) | 네이버 블로그는 에디터 안 AI 글쓰기(말투 반영 초안, 2023 기사). 워드프레스닷컴은 AI 어시스턴트(2026-02). Substack은 AI 탐지로 사람이 쓴 글을 앞세움(2026-07). 티스토리, 브런치는 공식 AI 글쓰기 기능을 찾지 못함. 대부분 초안을 대신 써 주는 방향. |
| 고객 (Customer) | 채용 담당자: 결과보다 판단 과정을 봄. 검색 독자: AI 요약이 있으면 클릭 8%, 없으면 15%(Pew). 관리자(나): 글 한 편을 내려면 제목, 요약, 카테고리, 표지, 점검을 모두 손으로 해야 함. |

### 3.2 문제 발굴

#### 3.2.1 문제 목록

| 번호 | 문제 | 타깃 | 솔루션 (후보) |
|---|---|---|---|
| P1 | 글을 발행하지 못함. 한 편을 내려면 제목, 요약, 카테고리, 표지, 점검을 손으로 해야 해서 기능만 늘고 글은 0편 | 관리자(나) | AI가 발행 전 제목, 요약, 카테고리를 제안하고 점검 |
| P2 | 처음 온 사람이 누구의 블로그인지, 무엇부터 읽을지 알 수 없음 | 채용 담당자 | 저자 소개와 대표 글을 첫 화면에 배치 |
| P3 | 글을 찾고 읽기 불편함. 첫 화면에 글이 없고 목록이 길며 본문 마크다운이 깨짐 | 모든 독자 | 목록과 글 상세 화면 개선, 마크다운 변환 |
| P4 | 검색과 공유로 새 독자가 들어오기 어려움(sitemap, RSS 없음) | 새 독자 | sitemap, RSS 추가, 공유 문구 제안 |

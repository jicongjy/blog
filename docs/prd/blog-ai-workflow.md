## 2. 개요

### 배경

이 블로그는 서비스 기획에 관한 글을 모아 두려고 직접 만들었고, 로그인, 방문 분석, 글 링크 미리보기가 이미 갖춰져 있어서 AI 기능을 바로 붙일 수 있다.

### 문제

1. 관리자인 나는 글 한 편을 올리려면 제목, 요약, 카테고리, 표지, 점검을 전부 직접 해야 해서 발행이 미뤄지고, 실제로 발행한 글이 0편이다.
2. 독자는 소개가 없고 글 목록이 길어서, 처음 온 사람이 어떤 글부터 읽을지 판단하기 어렵다.

이 두 문제는 3.2의 P1(관리자)과 P2, P3(독자)이다. 검색으로 새 독자가 들어오기 어려운 문제(P4)는 글과 독자가 생긴 뒤에야 효과가 있어서 이번에는 다루지 않는다(3.4.2).

### 솔루션: AI 기능으로 관리자와 독자의 워크플로우를 자동화한다

1. 관리자: 글을 올리기 직전에 AI가 제목, 요약, 카테고리를 제안하고 빠진 곳을 점검해서, 반복 작업이 줄고 발행이 앞당겨진다. AI는 글을 대신 쓰지 않는다.
2. 독자: 발행할 때 AI가 만든 요약을 글 목록과 글 맨 위에 보여 줘서, 독자가 글을 열기 전에 내용을 알고 읽을 글을 고를 수 있다.

### 3.2 문제 발굴

#### 3.2.1 문제 목록

문제를 네 가지 찾았다. 이번 프로젝트에서 푸는 것은 3.4에서 고르고, 고르지 않은 것은 후순위로 둔다.

| 번호 | 문제 | 타깃 | 솔루션 (후보) |
|---|---|---|---|
| P1 | 글 한 편을 올리려면 제목, 요약, 카테고리, 표지, 점검을 전부 직접 해야 해서, 올리는 일이 미뤄지고 결국 글이 0편이다. | 관리자(나) | 1. AI가 제목, 요약, 카테고리를 제안해서 고민하는 시간을 줄인다.<br>2. 올리기 전에 빠진 곳을 점검해서 덜 된 글이 올라가는 일을 막는다. |
| P2 | 처음 온 사람이 누구의 블로그인지 알 수 없어서, 어떤 글부터 읽어야 할지 몰라 읽을 이유를 찾지 못한다. | 처음 온 독자 | 1. AI가 만든 요약을 글 목록에 붙여서, 처음 온 사람이 읽을 글을 고를 수 있게 한다.<br>2. 첫 화면에 소개와 대표 글을 두어서, 무엇을 읽으면 되는지 바로 알 수 있게 한다. |
| P3 | 글을 찾고 읽기 불편해서 끝까지 읽기 어렵다.<br>1. 첫 화면에 글이 없어서 글을 찾으려면 따로 눌러야 한다.<br>2. 목록이 길어서 한눈에 비교하기 어렵다.<br>3. 인용과 링크가 기호 그대로 보여서 글이 덜 된 것처럼 보인다. | 모든 독자 | 1. 목록과 글 화면을 고쳐서 글을 쉽게 찾고 읽게 한다.<br>2. 본문 표시를 바로잡아서 글이 제대로 보이게 한다. |
| P4 | 검색이나 공유로 새 독자가 들어오기 어렵다.<br>1. 사이트맵이 없어서 검색엔진이 글을 찾는 데 도움을 받지 못한다.<br>2. 구독용 RSS가 없어서 독자가 새 글을 받아 볼 방법이 없다. | 새 독자 | 1. 사이트맵과 RSS를 추가해서 검색엔진과 구독자가 새 글을 찾을 수 있게 한다.<br>2. 공유용 문구를 AI가 제안해서 글을 퍼뜨릴 때 문장을 고민하는 시간을 줄인다. |

### 3.3 문제 검증

독자 설문은 하지 않는다. 그래서 문제별로 확인한 정도가 다르다.

| 문제 | 확인 방법 | 상태 |
|---|---|---|
| P1 발행이 힘들다 | 실제 글 한 편을 올리면서 단계별 걸린 시간을 직접 기록한다. | 8장 일정에서 구현 전에 측정한다. |
| P2 누구의 블로그인지 알 수 없다 | 3.1 데스크리서치에서 내가 화면을 보고 내린 판단이다. | 실제 독자에게는 확인하지 않았다. |
| P3 글을 찾고 읽기 불편하다 | 같음 | 실제 독자에게는 확인하지 않았다. |
| P4 검색과 공유로 들어오기 어렵다 | GA4에서 최근 28일 사용자 수와 유입 경로를 본다. | 방문자 수가 적어서 판단 근거가 약하다. |

P2와 P3은 제 판단만으로 세운 가설이라, 3.4의 RICE에서 Confidence를 낮게 둔다. 이번 기간에는 실제 독자 확인으로 올리지 않는다.

### 3.4 문제 최종 정의

#### 3.4.1 우선순위 결정 (RICE)

| 번호 | Reach (영향 범위, 1~10) | Impact (효과, 1~3) | Confidence (확신) | Effort (일) | 점수 |
|---|---|---|---|---|---|
| P1 발행 못 함 | 3 | 3 | 80% | 2 | 3.6 |
| P2 누구 블로그인지 모름 | 8 | 2 | 50% | 1 | 8.0 |
| P3 읽기 불편 | 8 | 1 | 50% | 2 | 4.0 |
| P4 새 독자 유입 어려움 | 5 | 1 | 80% | 1 | 4.0 |

1. 점수는 GA4 수치가 부족하고 독자 확인이 없어서 내가 상대적으로 매긴 추정값이라, 순위를 확정하는 근거가 아니라 판단 순서를 잡는 도구로만 쓴다.
2. P2와 P3은 실제 독자에게 확인하지 않아서 Confidence를 50%로 낮게 잡았고, 이번 기간에는 올리지 않는다.

#### 3.4.2 문제 최종 정의

핵심 문제: 관리자는 글을 올리기 번거롭고 독자는 읽을 글을 고르기 어려워서, 글도 읽는 사람도 생기지 않는다.

1. P1과 P2, P3은 따로 풀면 효과가 나지 않는다. 글이 없으면 보여 줄 것이 없고, 글이 있어도 고르기 어려우면 독자가 떠나기 때문이다.
2. 두 문제 모두 AI가 반복 작업을 대신하는 방식으로 풀 수 있어서, 이번 프로젝트 주제(독자 또는 관리자의 워크플로우를 AI로 자동화)에 맞아 핵심으로 정한다.
3. 소개 문구와 본문 기호 깨짐은 AI 없이 고칠 수 있어서 기본 개선으로 따로 처리하고, P4는 글과 독자가 생긴 뒤에야 효과를 볼 수 있어서 후순위로 둔다.

## 4. 해결 방안

### 4.1 솔루션 정의

관리자인 내가 글을 올릴 때 AI가 제목, 요약, 카테고리를 제안하고 빠진 곳을 점검해 주고, 그때 만든 요약을 독자가 글 목록과 글 맨 위에서 보게 해서, 글 올리기는 쉬워지고 독자는 읽을 글을 빨리 고르게 한다.

### 4.2 ASIS / TOBE

| 구분 | ASIS | TOBE |
|---|---|---|
| 컨셉 | 글을 올리는 모든 과정을 내가 직접 해서, 올리는 일이 미뤄진다. | 글은 내가 쓰고, 올리기 직전의 반복 작업은 AI가 제안해서 내가 고르기만 하면 된다. |
| 타겟 | 관리자와 독자가 같은 화면을 써서, 로그인하지 않은 방문자에게도 "글 작성하기"가 보인다. | 관리자는 발행 보조를 쓰고, 독자는 요약이 붙은 글 목록을 본다. |
| 비즈니스 모델 및 가격 정책 | 개인 블로그라서 별도 수익 모델과 가격 정책이 없다. | 별도 수익 없이 운영한다. 이 프로젝트는 결제 계정이 연결된 Blaze 요금제라 AI 사용은 종량제이며, 월 지출 한도를 ₩1,000으로 걸어 둔다. AI는 글을 올릴 때 관리자만 부르고 독자는 저장된 요약만 읽어서, AI 호출이 독자 수에 따라 늘지 않는다. |
| 기능 | 제목, 요약, 카테고리, 표지, 점검을 모두 직접 입력하고 확인한다. | 발행 직전에 AI가 제목, 요약, 카테고리를 제안하고 빠진 곳을 점검한다. 저장된 요약은 글 목록과 글 맨 위에 보인다. |
| 디자인 | 글 하나가 한 화면을 차지하고 같은 목록이 두 번 나와서, 글 4개인데 홈 길이가 4,744px이다. | 글 목록 카드에 요약을 넣어 목록을 짧게 하고, 글 맨 위에 요약 상자를 둔다. |

### 4.3 예상 성과

1. 올리는 일이 쉬워져, 공개 글 수가 늘어난다.
2. 글 한 편을 올리는 시간이 줄어든다.
3. 요약을 보고 글을 고르므로 글을 여는 비율과 끝까지 읽는 비율이 올라갈 것으로 기대한다. 이번 기간에는 판정하지 못하고 릴리스 후 28일 동안 관찰한다.

#### OKR

- **O**: 글을 올리는 일이 쉬워지고, 틀리지 않은 요약을 독자에게 보여 주는 블로그가 된다.
- **KR1**: 릴리스 목표일(11-25)까지 공개 글을 0편에서 3편 이상으로 늘린다.
- **KR2**: 글 한 편을 올리는 시간을 AI 구현 전보다 30% 줄인다.
- **KR3**: AI 제안의 절반 이상을 그대로 또는 고쳐서 쓴다.
- **KR4**: 생성한 요약에서 본문과 맞지 않는 요약이 0건이다.

### 5.3 릴리스 후 관찰 지표 (릴리스 후 28일, 목표 수치 없음)

이번 기간에는 방문 데이터가 부족하고 GA4 보고서 반영이 늦어서 이 두 지표의 효과를 판정하지 못한다. 공개 글 수는 효과 지표가 아니라 4.3의 목표(KR1)로만 둔다.

### 6.2 화면과 동작

#### 6.2.1 에디터 (관리자, /write)

| 상태 | 화면 | 다음 동작 |
|---|---|---|
| 처음 | 제목, 요약, 카테고리, 표지, 본문 입력칸은 지금과 같다. 본문 아래에 "AI 제안 받기" 버튼이 있다. 본문이 비어 있으면 버튼을 누를 수 없고 "본문을 먼저 쓰세요"를 보여 준다. | 본문을 쓰면 버튼이 켜진다. |
| 진행 중 | 버튼이 "제안 만드는 중"으로 바뀌고 다시 누를 수 없다. 입력칸은 계속 고칠 수 있다. | 10초 안에 끝나지 않으면 실패로 본다. |
| 성공 | 제목, 요약, 카테고리 제안이 각각 한 개씩 입력칸 옆에 나타난다. 제안은 입력칸을 자동으로 덮어쓰지 않고, 항목마다 "쓰기"를 눌러야 칸에 들어간다. 들어간 뒤에도 직접 고칠 수 있다. | 쓰기, 고쳐 쓰기, 무시 중 하나를 고른다. |
| 실패 | "제안을 받지 못했습니다. 직접 입력해 주세요"를 보여 주고 입력한 내용은 그대로 둔다. | 다시 시도하거나 직접 입력해 발행한다. |
| 횟수 소진 | 이 글에서 쓸 수 있는 제안 횟수를 모두 써서 버튼이 꺼진다. | 직접 입력해 발행한다. |
| 발행 누름 | 제목, 요약, 카테고리 중 비어 있는 것이 있으면 발행하지 않고 어느 항목인지 알려 준다. 표지가 비어 있으면 알리되 발행은 막지 않는다. | 채우고 다시 누르거나 표지 없이 발행한다. |

#### 6.2.2 글 목록 카드 (독자)

표지, 카테고리, 제목, 요약(두 줄까지 보이고 넘치면 줄임), 날짜 순서로 보여 준다. 요약이 없는 예전 글은 요약 줄만 빼고 나머지는 그대로 보인다.

#### 6.2.3 글 맨 위 요약 상자 (독자)

제목 아래, 본문 위에 "요약"이라는 이름표와 함께 상자로 보여 준다. 로그인하지 않은 방문자에게도 보인다. 요약이 없는 글은 상자를 만들지 않는다.

### 6.3 데이터

| 데이터 | 저장 위치 | 내용 |
|---|---|---|
| 제목, 카테고리, 표지 | 글의 기존 필드 | 지금과 같다. |
| 요약 | 글의 요약(excerpt) 필드 | 관리자가 고른 최종 요약이다(D16). 독자가 글을 열 때 AI를 부르지 않는다. |
| 사용 기록(F7) | 글의 기록 필드 한 곳 | 항목(제목, 요약, 카테고리)마다 제안값과 최종값, 호출한 횟수, 마지막 호출의 성공 여부와 응답 시간(밀리초). 글 문서에 들어가므로 계정 정보나 개인 정보는 넣지 않는다. |

제안 반영 방식(KR3)은 이 기록에서 항목마다 "그대로 씀, 고쳐 씀, 안 씀"으로 나눠 센다. 최종값이 제안값과 같으면 그대로, 비슷하지만 다르면 고침, 전혀 다르면 안 씀으로 본다.

### 6.4 AI 호출 명세

| 항목 | 내용 |
|---|---|
| 호출 방법 | 관리자의 브라우저에서 Firebase AI Logic(Agent Platform Gemini API)을 부른다. App Check(Fraud Defense)를 통과한 요청만 받는다. |
| 보내는 것 | 작성 중인 제목(비어 있을 수 있음), 본문, 카테고리 이름 목록(D17). |
| 받는 것 | 제목 한 개, 요약 한 개, 카테고리 한 개. 구조화된 형식(JSON)으로 받는다. |
| 지시 내용 | 본문에 없는 내용은 쓰지 않는다(KR4). 요약은 120자 안팎, 두 문장 이하로 쓴다. 카테고리는 보낸 목록 안에서만 고른다. AI는 글을 대신 쓰지 않는다(D9). |
| 시간 제한 | 10초. 넘으면 실패로 처리한다(F6). |
| 횟수 제한 | 글 한 편에서 제안을 5회까지 부를 수 있다. 구현하면서 조정하면 이 문서와 D에 기록한다. |
| 모델 | gemini-3.5-flash-lite(안정 버전의 저비용 모델, D32). 제안 품질이 낮으면 모델을 바꾸고 D에 기록한다. |
| 호출 권한 | 화면에서는 관리자 로그인일 때만 버튼을 보여 준다(F5). 서버 쪽은 App Check가 막고, 관리자 계정까지 서버에서 가려내는지는 구현할 때 확인한다. |

## 7. 비기능적 요구사항

| 항목 | 요구사항 | 이유 |
|---|---|---|
| 개인정보 | AI에 보내는 정보는 작성 중인 글의 제목, 본문, 카테고리 이름뿐이다. 계정 정보와 방문자 정보는 보내지 않는다. | AI 서비스로 나가는 정보를 글 내용으로 한정하려고 |
| API 키 | 키를 소스 코드와 저장소에 넣지 않고 Firebase AI Logic을 쓴다. | 저장소에 키가 남으면 되돌리기 어렵다. |
| 호출 제한 | 로그인한 관리자만 호출하고, 글 한 편에서 제안을 부를 수 있는 횟수를 제한한다. 횟수는 6.4에 적은 대로 글 한 편당 5회이다. | 종량제라 호출이 늘면 비용이 생기고, 월 지출 한도에 닿으면 서비스가 멈춘다. |
| 응답 시간 | 제안은 10초 안에 나와야 하고(5.2 합격 기준), 기다리는 동안 진행 중임을 보여 준다. 응답 시간은 F7로 기록해 판정한다. | 기다리는 시간이 길면 직접 쓰는 편이 빠르다. |
| 비용 관리 | 결제 계정이 연결된 프로젝트라 AI 사용은 후불 종량제다(D14, D28). Gemini Developer API는 선결제 크레딧을 요구해서 Agent Platform Gemini API를 쓴다(D32). 서비스별 월 지출 한도 ₩1,000을 걸어 두었고 Agent Platform API도 그 목록에 있다. 한도에 닿으면 서비스가 그 달 동안 멈춘다. 멈추면 AI 제안을 끄고 직접 입력으로 쓴다(F6). 호출 한도 숫자는 확인하지 못했다. 발행 보조의 인증에 쓰는 Fraud Defense는 월 10,000건까지 무료이지만 이 한도 목록에 없어서 사용량을 따로 확인한다(D31). | 비용이 크게 늘면 개인 블로그에서 유지하기 어렵다. |

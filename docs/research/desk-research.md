# 데스크리서치 v0.1 (PRD 3.1)

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-11-23 |
| 목적 | 블로그에 넣을 AI 워크플로우 기능을 정하기 전에 블로그 현황, 경쟁 환경, 독자를 확인한다 |
| 범위 | 블로그 화면과 코드 점검, 웹 검색 7회. 사용자 조사(설문)와 GA 실측 수치는 아직 없음 |

## 1. 자사(Company): 블로그 현황

2026-11-23 배포 화면과 저장소를 직접 확인한 결과.

| 구분 | 확인한 사실 |
|---|---|
| 콘텐츠 | 공개 글 4개. 모두 2026-11-17 작성, 읽는 시간 1분, 본문 약 680자 예시 글. 제목 "제목", 요약 "요약입니다"인 시험 글이 공개 상태 |
| 정체성 | 사이트 이름 "기획 노트", 설명 "서비스 기획에 관한 글을 모아 둔 블로그". 저자 이름, 소개, 포트폴리오 링크 없음 |
| 첫 화면 | 데스크톱은 소개 문장과 카테고리만 보이고 글이 없음. 모바일은 두 화면을 내려야 첫 글이 보임 |
| 목록 | 글 하나가 한 화면을 차지해 글 4개 홈 길이가 4,744px. 같은 글 목록이 왼쪽 Notes와 오른쪽 카드로 두 번 나옴 |
| 글 상세 | 인용(`>`)과 링크(`[텍스트](주소)`)가 기호 그대로 보임. 제목이 본문 첫 소제목으로 한 번 더 나옴 |
| 주제 외 요소 | 헤더에 영어 명언 띠, 공휴일 D-day, 초 단위 시계. 최근 커밋 상당수가 이런 API 실습 기능 |
| 관리 기능 노출 | 로그인하지 않은 방문자에게도 "글 작성하기" 메뉴가 보임 |
| 검색 기반 | sitemap.xml, robots.txt, RSS 모두 404. 글별 공유 미리보기(OG)는 있음 |
| 기술 기반 | React + GitHub Pages + Firebase(Firestore, 구글 로그인). GA4 측정 ID 등록 완료, 이벤트(완독, 공유, 검색, 좋아요, 스크랩) 구현 완료 |
| AI 기반 | 별도 API 키 없음. 같은 Firebase 프로젝트에서 Firebase AI Logic(Gemini Developer API)을 켜면 키를 직접 다루지 않고 무료 요금제로 호출 가능([Firebase 문서](https://firebase.google.com/docs/ai-logic/get-started)) |

## 2. 경쟁(Competitor): 블로그 플랫폼의 AI 기능

| 플랫폼 | 확인한 내용 | 근거 수준 |
|---|---|---|
| 네이버 블로그 | 에디터 안 "AI 글쓰기"로 사용자 말투를 반영한 초안 생성 | 언론 기사(2023), [디지털데일리](https://www.ddaily.co.kr/page/view/2023101513440106248) |
| 네이버 검색 | AI 브리핑 이용자 3천만 명, 전체 검색 쿼리 약 20% 처리(2026-04 발표 기준) | 2차 보도 |
| 워드프레스닷컴 | AI 어시스턴트 출시(2026-02): 편집, 디자인, 이미지 | 2차 정리 글 |
| Substack | 2026-07 AI 탐지와 작성자 투명성 기능. 사람이 쓴 글을 앞세우는 방향 | [Press Gazette](https://pressgazette.co.uk/news/substack-promotes-human-content-with-scan-for-ai-feature/), [NPR](https://www.npr.org/2026/08/12/nx-s1-5919251/substacks-new-ai-detection-feature-has-divided-its-community) |
| 티스토리, 브런치 | 이번 검색에서 공식 AI 글쓰기 기능 공지를 찾지 못함. 외부 유료 초안 서비스는 있음 | 확인 못 함 |
| Ghost, Medium | 출처끼리 내용이 엇갈려 판단 보류 | 확인 못 함 |

시사점: 큰 플랫폼의 AI는 "초안을 대신 써 주는" 쪽이고, 반대편에서는 AI 글에 대한 불신(Substack 탐지 기능)이 커지고 있다. 개인 블로그는 플랫폼 기능을 기다릴 필요 없이 자기 워크플로우에 맞춘 AI를 직접 붙일 수 있다.

## 4. SWOT

| | 도움 | 방해 |
|---|---|---|
| 내부 | **S 강점**: 직접 만든 블로그라 기능을 자유롭게 붙임. Firebase, GA 이벤트, 글별 OG가 이미 있음. 잡지형 디자인 방향이 정해져 있음 | **W 약점**: 실제 글 0편, 시험 글 공개. 저자 정보 없음. 첫 화면과 목록의 사용성 문제. 검색 기반 파일 없음. 주제와 무관한 위젯 |
| 외부 | **O 기회**: 채용 측은 판단 과정을 담은 글을 원함. 무료 Gemini를 키 없이 쓸 수 있음. 국내 주요 플랫폼에서 발행 점검형 AI는 확인되지 않음 | **T 위협**: AI 요약 검색으로 클릭 감소. AI가 쓴 글에 대한 불신. 큰 플랫폼과의 노출 경쟁 |

## 5. 문제 후보 (PRD 3.2로 넘길 것)

| 번호 | 문제 | 대상 | 근거 |
|---|---|---|---|
| P1 | 글을 발행하지 못한다. 한 편 내는 데 손이 많이 가서 기능만 늘고 글은 0편 | 관리자 | 1장 콘텐츠, 3장 관리자 |
| P2 | 처음 온 독자가 누구의 블로그인지, 무엇부터 읽을지 알 수 없다 | 채용 담당자 | 1장 정체성, 첫 화면 |
| P3 | 글을 찾고 읽기 불편하다. 첫 화면에 글이 없고, 목록이 길고, 본문이 깨진다 | 모든 독자 | 1장 첫 화면, 목록, 글 상세 |
| P4 | 검색과 공유로 새 독자가 들어오기 어렵다 | 새 독자 | 1장 검색 기반, 3장 검색 독자 |

## 6. 아직 모르는 것 (3.3 문제 검증에서 확인)

- 실제 방문 수와 유입 경로: GA4 화면에서 최근 28일 사용자 수, 유입 경로, 글별 조회수를 확인해야 함
- 독자가 정말 P2, P3을 불편하게 느끼는지: 수강생이나 지인 3~5명에게 첫 화면을 5초 보여 주고 "누구의 무슨 블로그인가"를 묻는 짧은 설문
- 관리자의 발행 병목이 어디인지: 실제 글 한 편을 발행하면서 단계별 걸린 시간 기록
